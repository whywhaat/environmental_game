# Общее состояние переговоров

> Статус применения: это аналитическая спецификация. Классификация правил и необходимые решения заданы в [decision_register.yaml](decision_register.yaml); источник процедур — исходный регламент, а не эта рекомендация. Раздельные статусы объектов определены в [agreement_lifecycle.md](agreement_lifecycle.md). Пересмотр ratified-соглашения не поддерживается до DEC-04, игровой статус намерений — до DEC-03.


Основания: S-GAME, S-NEGOTIATION, S-PROTOCOL, S-VOTE и S-REQUEST. Это описание данных для будущей реализации, не новая архитектура хранения и не требование конкретной технологии.

## Состав общего состояния

| Раздел | Содержимое |
|---|---|
| Идентичность | session_id, scenario_id/version, rules_version, тип учебного результата и доказательство утверждения применённой конфигурации |
| Участники | Пять постоянных agent_id, публичные имена, ссылки на профили; orchestrator и judge — служебные роли |
| Процедура | round_id, cycle_number, current_speaker, expected_next_speaker, выделенный slot_id, счётчик раунда 2, остаток, число использованных повторных рассмотрений |
| Журнал | Неизменяемая последовательность событий; отдельно валидированная проекция |
| Реестр позиций | initial/current/history по роли и issue_id, без публикации приватных полей |
| Реестр предложений | ID/версия, предмет, автор, собственные и запрошенные чужие обязанности, статус, альтернативная ветвь |
| Реестр условий | Владельцы, точный текст/структура, подтверждения, условия активации, история lifecycle, отменённые/заменённые версии |
| Факты и основания | claim_id, knowledge_type, source_refs, сопоставимость измерений, статус достоверности и границы вывода |
| Ресурсы | План, единицы, лимиты, предложения, резервации, реальное подтверждение доступности и отдельно исполненные платежи |
| План мероприятий | Результат, ответственный владелец, предшественники, длительность, окно срока, точка отсчёта, ресурс и способ проверки |
| Споры | unresolved_dispute по предмету, позициям, источникам, влиянию и следующему шагу |
| Протоколы | agreement_id/version, тип, список условий и их версий, открытые вопросы, источник каждого пункта, admission_status |
| Голосование | Неизменная допущенная версия, пять отдельных бюллетеней, скрытый сбор и совместное раскрытие, итог |
| Тип документа | intent_protocol / final_agreement; сопоставление исходным conditional_intent / confirmed_plan требует DEC-02 |
| Завершение сессии | no_agreement / administrative_interruption либо результат по отдельно подтверждённому регламенту; победа не выводится из типа документа |

Согласие владельца с условием, тип документа, его ратификация и игровая победа — разные данные. Исходные названия conditional_intent/confirmed_plan сохранены в источниках; новые аналитические названия не являются миграцией приложения. До DEC-03 intent_protocol не получает установленную игровую ратификацию или победу. Принятие final_agreement также требует применимой утверждённой процедуры и всех обязательных критериев.

## Событие и порядок истории

Для каждого события: `event_id`, `sequence_number`, `session_id`, `scenario_version`, `event_kind`, `actor_id`, `round_id`, `slot_id`, `public_turn_number` при наличии, `caused_by`, `target_refs`, `payload`, `source_refs`, `visibility`, `validation_status`, `verdict_ref`, `recorded_at`, `effective_at` при необходимости.

`sequence_number` задаёт единый порядок регистрации. `recorded_at` не заменяет порядок и не доказывает время измерения или принятия внешнего решения. Для поздно полученного документа сохраняются отдельно дата самого документа, дата получения и событие его проверки. Проекция не переписывается незаметно задним числом.

Различаются публичное сообщение агента, служебный слот/переход оркестратора, вердикт судьи, проверка источника, обновление сценария и голос. Публичный ход и связанный с ним вердикт — два события, но только один переговорный ход. Отклонённая попытка остаётся в журнале; её недопустимый финансовый эффект не применяется.

Технический дубль с тем же event_id не создаёт новое обязательство. Разные события с одним ID и разным содержанием — дефект целостности, требуется разбирательство, не «последняя запись победила». Пропущенное исходное событие оставляет проверку зависимого изменения `pending_evidence`; причина не придумывается.

## Общие инварианты

1. В один момент только один переговорный слот; НКО передаёт управление оркестратору, а не самостоятельно начинает новый цикл.
2. Счётчик раунда 2 монотонен; коррекция в разрешённом слоте учитывается, служебные события и голоса — нет. Возврат из раунда 3 не сбрасывает использованные ходы.
3. У каждого условия есть конкретная версия, владелец каждого обязательства и отдельное подтверждение. Согласие одного участника не дописывает согласие остальных.
4. Новая версия протокола не меняет старую; голоса и допуск относятся только к той версии, для которой получены.
5. Нет неограниченного подтверждённого ресурса; суммы целые рубли, условные предложения отделены от подтверждённой доступности.
6. Противоречие не исчезает после копирования условия в другой документ. Сохраняется связь от исходной реплики до пункта протокола и результата голосования.
7. Спор с материальным влиянием блокирует зависимый обеспеченный план; независимая дискуссия и явно ограниченные намерения могут продолжаться по исходному регламенту.
8. Принятие учебного протокола не создаёт автоматически реальное обязательство и не подтверждает выполнение услуги.

## Формат unresolved_dispute

`dispute_id`, `issue_id`, `conflict_types` (список, может быть пустым при обычном расхождении интересов), `assertions` с автором/версией/источником, `affected_conditions`, `affected_protocol_versions`, `materiality`, `status: unresolved_dispute`, `owner_of_next_check`, `requested_evidence`, `next_review_condition`, `resolution_event` после разрешения.

Обычный спор «ежемесячные или еженедельные встречи» не обязан получать FACTUAL_CONFLICT. Ответственный за следующий запрос может быть определён как организационное действие; это не наделяет его правом гарантировать ответ третьей стороны. Закрытие спора требует события с основанием, а не только более уверенного ответа модели.

## Утверждённое изменение сценария

У обновления должны быть основание разрешённой процедуры, уполномоченный утверждающий, прежняя/новая версия, изменённые ограничения, момент действия и список затронутых позиций/условий/протоколов. Агент может попросить обновление, но не утвердить себе лимит. Старые нарушения не оправдываются задним числом новым пределом. Уменьшение лимита ниже действующей нагрузки вызывает отдельную проверку и новый план, не молчаливое исчезновение обязательства.

Порядок такого утверждения в исходном проекте не определён полностью: спецификация задаёт необходимые свидетельства, но не назначает нового владельца полномочий. Это вопрос DEC-07 в [handover](architect_handover.md).

## Фрагмент последовательности

Публичное предложение P-1 v1 → вердикт по предложению → контрпредложение P-2 v1 → собственные подтверждения точных условий → запись согласованного плана → проект протокола A v1 → сверка → допуск A v1 → пять скрыто собираемых голосов → раскрытие → ратификация либо отказ. При обнаружении ошибки формируется новая цепочка коррекции; предыдущая остаётся доступной для аудита.
