# RAG, контекст, источники и приватность

Оценка RAG-контура в текущем Python — **50/100**, статически. Сильные стороны: фильтр по аудитории до выдачи, ID/статусы источников, запрет исполнения команд внутри цитат, различение непроверенного права. Слабые стороны: рассинхронизация редакций, потеря трассировки через секретаря, отсутствие RAG у судьи и неопределённая выдача служебных материалов. Поведенческие атаки и работа live Chroma не тестировались.

## Фактический маршрут

[rag.py](../../langflow/custom_components/my_components/rag.py), 42–73, распаковывает встроенный CORPUS_B64, вычисляет hash, создаёт коллекцию с именем по hash и загружает 159 записей с embeddings. Проверяются модель/размерность, конечность вектора и уникальность chunk_id при заполнении. JSONL напрямую этим компонентом не читается. **Разобранные 159 записей совпадают с `full_embeddings.jsonl`**, что не доказывает совпадение с текущими Markdown.

[dialog.py](../../langflow/custom_components/my_components/dialog.py), 130–175, сопоставляет точное display name одной из пяти кратких ролей, строит query из роли, intent и двух последних публичных реплик, получает embedding и делает Chroma query с `where={'visible_'+role:True}`. top_k ограничен 1–8, default 4, каждый текст обрезается до 3500 символов. Ошибка имени даёт KeyError до защищённого блока; обработка такого сбоя относится к PA-19; использование стабильного actor_id предлагается для устранения этой зависимости, это не подтверждённая утечка ACL.

В Python retrieval вызывается только перед REPORT и PLEDGE и передаётся **личному секретарю**. Участник получает его краткую записку, без прямых RAG-фрагментов, общего ledger и полного регламента. QUESTION/ANSWER/VOTE не делают новый retrieval. В flow `_rag_context` вызывается на всех трёх этапах, фрагменты добавляются прямо в Human. Эти варианты нельзя смешивать в утверждении «агент всегда видит источники».

## Реальные межисточниковые расхождения

- Фрагмент **NGO-04**, `full_embeddings.jsonl:50`, прямо задаёт нулевой вклад НКО в реконструкцию; её config/flow дают максимум 10 млн. Это релевантное противоречие, которое может прийти самой роли, а не только расхождение с недоступной архитекторской документацией (PA-12).
- **REG-04**, строка 34, отключает федеральный грант по умолчанию до отдельного условия запуска. Ролевой общий блок позволяет SET с субсидиями «под гарантии» (PA-03).
- Фактические **J-04/J-08/J-09** корпуса требуют полного подтверждённого бюджета, одной версии, подтверждений владельцев и пяти независимых бюллетеней. Исполняемая логика покрывает часть этих требований, а судье сами фрагменты не приходят (PA-10/14/25).
- Компактные `rag_docs_gorod_N/` — отдельная редакция. Например, `07_judge_rules.md:81–82` говорит о действующем порядке и парсере; **J-10** фактического корпуса, JSONL:64, осторожнее: полный актуальный текст и применимость не удостоверены, само упоминание парсера не доказывает получение. Аудит не проверял актуальность закона и не повторяет исходную правовую формулировку как собственный вывод (PA-18).

## Защита от подмены инструкций

[rag_prompt_config.py](../../config/prompts/rag_prompt_config.py), 5–11, явно говорит: источники — данные, цитируемые команды не исполнять, правовой статус учитывать, ссылаться на chunk_id. `<source>` задаёт видимую границу текста. Встроенный flow имеет аналогичный intro. Поэтому утверждение «защиты от RAG-инъекций вообще нет» было бы неверным.

Защита остаётся инструкцией HumanMessage. История чужих выступлений и результат секретаря не имеют столь же явного общего правила доверия. Секретарь может потерять исходный статус и ID, а источник может сам содержать правила ролей/J-свод. Не определено, какой утверждённый manifest разрешает превращать такой текст в правило запуска. Успешная атака не показана; PA-11 — потенциальный риск. Предлагается закрепить приоритет доверенных правил на верхнем уровне, сохранять метаданные при суммаризации и проверять финансовые/процедурные эффекты независимо от текста LLM.

## Приватность: что подтверждено и что неизвестно

Фильтр visible применяется до выдачи. Прямой отправки чужого приватного профиля в промпт другого игрока не обнаружено. Полный profile в личном контексте относится к самому участнику. Публичная история закономерно может содержать сведения, которые их владелец уже произнёс; запрет дальнейшего распространения из самого факта «скрытого бюджета» автоматически не выводится.

Однако ответы не проверяются на непреднамеренное раскрытие своего скрытого intent. Query включает intent и отправляется выбранному embeddings API; политика допустимой передачи приватных данных провайдерам в репозитории не обнаружена. Это вопрос доступа и конфигурации, не доказанная несанкционированная отправка.

`prompt_logs` и `players` с приватным содержимым входят в общий Data результата, полные промпты игрока пишутся в WARNING. Последующий судья легитимно получает все профили для разбора, но `ReportController` может показать его текст в общем отчёте. Неизвестны ACL журналов, UI и конечная аудитория. PA-09 фиксирует маршрут возможного раскрытия, **не утверждает состоявшуюся межагентную утечку**. Нужны согласованные представления public/role/judge/architect, внешние ACL и политика служебных логов.

## Отсутствие и конфликт источника

Секретарь уже должен различать неподтверждённое, ANSWER допускает признание недостатка данных, правовые фрагменты содержат legal_review_required. Но для всех пяти ролей нет единой явной процедуры коллизии карточка↔роль↔RAG↔публичное утверждение. Ошибка retrieval прерывает выполнение; пустая выдача/отсутствие нужного документа не становится автоматически структурированным запросом доказательств. Разделить «источник не найден», «источник конфликтует» и «источник не даёт полномочия» — предлагаемая доработка PA-17/19.

Пересборка корпуса, обновление embeddings и включение CONS-документов этим аудитом не выполнены. Сначала нужны DEC-01/08/09/10 и отдельное разрешение, включая видимость каждого материала. Архитекторский пример не становится общедоступным правилом только потому, что его удобно искать через RAG.
