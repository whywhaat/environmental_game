# Оркестратор и передача слова

Отдельного LLM-агента «оркестратор» в приложении не найдено. Очерёдность задаёт Python. В текущем варианте LLM председателя выбирает следующий этап из программно разрешённых; в экспортированном варианте адресат из текста влияет на очередь. Поэтому оценка оркестратора относится к механизму и сборке инструкций, а не к несуществующему отдельному System prompt.

## Два подтверждённых варианта

## Порядок и обозначение передачи слова

В Python участник не может фактически сменить следующего говорящего через TO: это положительное ограничение контроля. Однако роль обещает такую возможность, а адресат для завершения реплики не сообщён. Нарушение формата передачи слова не получает отдельного вердикта; команда просто исчезает. В QUESTION адресат — докладчик, но следующий говорящий часто другой задающий вопрос. Их нельзя считать одним объектом (PA-06).

В flow программа сохраняет окончательное управление, но семантика TO делегирует выбор адресата агенту. `_extract_addressed_player` рассматривает также обычные `@mentions`; несколько адресатов не вызывают явного отказа — выбирается первый подходящий. Это не соответствует строгому запрету двух адресатов в текстах. Четыре обращения пары являются программным ограничением, которое не объяснено в ролевой инструкции. Переносить сюда фиксированную очередь из демонстраций без решения команды нельзя.

[game_config.yaml](../../ecological_simulator_knowledge/04_game_rules/game_config.yaml), 18–25, 40–53, предлагает фиксированную очередь только для раунда 2 и лимит 30; `approved=false`. [step_by_step/turn_taking_rules.md](../../ecological_simulator_knowledge/08_negotiation_examples/step_by_step/turn_taking_rules.md) — демонстрационная модель передачи управления оркестратору. Ни один из этих файлов сейчас не управляет Python или flow. Принцип «оркестратор назначает, агент обозначает передачу» — желаемый контракт пользователя для оценки; действующие различия сохранены как PA-04/06, не исправлены.

## Доставка правил и состояние

В Python `rules_prompt` по умолчанию пуст. `meeting_rules` не вызывается загрузчиком компонента; вручную переданный текст получает только секретарь. В flow узел регламента подключён, но `_build_prompt_phase1/2` не используют аргумент `rules_prompt`, а phase3 его не принимает. Сама связь в графе не доказывает доставку текста в LLM (PA-25).

Состояние имеет только `contribution/share`. История копируется, что полезно для разбора, но не содержит нормализованных условий, типа документа, версии, отдельных согласий владельцев и оснований активации. Изменение SET во втором круге перезаписывает текущую сумму; связь с прежними встречными обещаниями остаётся только в тексте. После итогового решения программа завершает выполнение: процедуры изменения ratified-документа нет, и аудит её не вводит (PA-08).

## Нестандартные ответы и завершение

Python пропускает некорректный PLEDGE без изменения ledger, сохраняет отказ и не превращает неизвестный бюллетень в «ЗА». Но неизвестный бюллетень становится воздержанием, тогда как проектный регламент различает отсутствие голоса и abstain; это расхождение редакций, а не основание самостоятельно изменить парсер. В flow любой нераспознанный бюллетень становится «ЗА» — подтверждённый опасный дефект (PA-13).

В flow последние N строк с подстрокой ACCEPT не доказывают N разных согласий; возможны повторные говорящие и отрицание «не ACCEPT» (PA-23). Финансовое покрытие останавливает торг независимо от согласования оператора, воды и мониторинга. В обоих вариантах сформированный протокол содержит фиксированные условия (PA-02). Номер этапа и успешный возврат компонента не дают права называть результат окончательным обеспеченным соглашением.

План будущей коррекции: сначала решить DEC-01 о применимой редакции, затем согласовать контракт очереди, состояния и допуска. После отдельного разрешения изменять оркестратор и проверять граничные сценарии. Согласование не требуется для настоящего отчёта; для реализации оно ещё не дано.
