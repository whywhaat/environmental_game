# Непротиворечивость поведения и состояния

Текст роли задаёт мотивацию, но не может гарантировать сохранность ранее принятого условия, остаток ресурса и идентичность версии. В текущем Python есть полезная история со снимками state и проверка собственного PLEDGE. При этом состояние не моделирует неденежные условия, подтверждения их владельцев и зависимости. Ниже аналитическая оценка, а не активация правил `docs/agent_consistency/`.

## Что может нарушиться

| Вопрос | Фактический механизм | Ограничение |
|---|---|---|
| Забыть прежнюю позицию | Секретарь видит историю, игрок получает 1500 символов записки | Собственная история исключена из other_speeches; PA-07/16 |
| Противоречить себе | Роль просит встречное условие для уступки, судья читает историю PLEDGE | Нет явной связи версии и причины изменения; PA-07/08 |
| Поменять деньги без причины | Judge review оценивает объяснение и минимум слов | Нет формального сопоставления причины и старого условия; flow не делает review; PA-01/08 |
| Принять несовместимые обязательства | Сохраняется последняя сумма | Стройка, вода, мониторинг и ущерб не представлены отдельными обязанностями; PA-03/08 |
| Назначить чужие ресурсы | Python judge отклоняет чужой SET | Flow не проверяет владельца; неденежное назначение не проверяется системно; PA-01/10 |
| Изменить утверждённые условия | После завершения текущая функция прекращается | Процедуры пересмотра нет; отсутствие интерфейса не является её разрешением; PA-08 |
| Сослаться на неизвестный факт | RAG содержит статусы, секретарь должен не выдумывать числа | Контекст неполон, цитаты не валидируются, у роли есть категорические прогнозы; PA-15/17 |

## Девять терминов не являются одним автоматом состояний

Основание сравнения: [agreement_lifecycle.md](../agent_consistency/agreement_lifecycle.md), 19–96; [decision_register.yaml](../agent_consistency/decision_register.yaml), DEC-02–05. Это объектная аналитическая модель, не реализованный контракт.

| Термин | Объект в аналитической модели | Что есть в runtime |
|---|---|---|
| proposed | Версия предложения | Свободная речь/SET; отдельного предложения с ID нет |
| conditionally_accepted | Предварительное согласие конкретного участника по условию | Может присутствовать в тексте SPEAK; отдельной записи нет |
| accepted | Согласие владельца с точным текстом условия | Поле judge accepted означает принятую проверку взноса; семантика иная |
| rejected | Предложение, согласие либо документ — каждый в своей области | REJECTED в истории для неуспешного PLEDGE; passed=false для документа, без объектной связи |
| withdrawn | Отзыв непринятого предложения без замены | Специального перехода нет; новый SET не доказывает корректный отзыв |
| superseded | Заменённая версия предложения/проекта со ссылкой | Последняя сумма перезаписывает текущую, история сохраняется без replacement_ref |
| included_in_protocol | Связь условия и версии документа | Условия в рендерере фиксированы, источник включения не проверяется |
| ratified | Утверждение допущенной версии документа | passed/«протокол принят» без versioned admission; нельзя считать эквивалентом |
| active | Вступившее в силу конкретное обязательство | Не моделируется; ни голос, ни SET не доказывают исполнение |

Названия `intent_protocol` и `final_agreement` отсутствуют в действующих шаблонах. Нельзя задним числом переименовать любой passed в final_agreement. Для окончательного соглашения проверяются подтверждённые источники финансирования, оператор и исполнители, защита жителей, мониторинг и контроль, если этого требует выбранный регламент; отсутствие данных не делает обязательный пункт необязательным. Намерения должны сохранять неизвестность и условия подготовки, их игровой статус — открытый DEC-03. **Автоматическая победа или ратификация намерений не установлена.**

Обоснованное изменение до утверждения может быть новым предложением с причиной и подтверждениями; это не право незаметно отменить принятую обязанность. Доработка отклонённого документа в проектном GAME-VOTE описана отдельно, с новой версией и голосами в остатке процедуры. После ratified переход пересмотра **не поддержан до отдельного решения DEC-04**. В рамках аудита не создаются новый раунд, отмена старой версии или механизм повторного утверждения.

## Двенадцать нестандартных ситуаций

«Ожидаемое» — предлагаемая цель проверки, частично поддержанная существующими текстами; обязательность деталей требует решения команды. Ни один из сценариев ниже не выдаётся за прогон реальной модели.

| Ситуация | Ожидаемое поведение | Потенциально ошибочное поведение и имеющийся пробел | Где исправлять после разрешения |
|---|---|---|---|
| 1. Противоречивые данные | Назвать обе версии/источники, запросить активную карточку, не выбирать удобный лимит | НКО видит 10 млн в роли и ноль в NGO-04; берёт разрешающий вариант; PA-12/18 | Manifest редакции, RAG, инструкция разрешения коллизии |
| 2. Недостаточно информации | Явно назвать пробел и запросить источник; отделить предварительное действие от гарантированного результата | Придуман оператор/концентрация или обещана субсидия; PA-03/10/17 | Промпт и допуск состояния, semantic review |
| 3. Требование невозможного | Объяснить предел, предложить допустимую альтернативу или мотивированный отказ | Holding принимает сумму выше лимита ради «спасения сделки»; flow её применяет; PA-01/15 | Проверка ресурса, роль/компромисс |
| 4. Предыдущий участник нарушил правило | Указать предмет возражения и источник; действовать в своём слоте, передать вопрос судье | Агент копирует ложный факт, сам назначает наказание или меняет очередь; PA-06/10/11 | Разделение реплики и вердикта, оркестратор/судья |
| 5. Выход за полномочия | Отказать в чужом решении, предложить запрос компетентной стороне | NGO обещает лабораторный результат без исполнителя; город гарантирует федеральный бюджет; PA-03/10 | Мандаты, ресурсный реестр, текст роли |
| 6. Провокационная реплика | Ответить содержательно, не считать оскорбление поручением, сохранить процедуру | Ответная угроза/раскрытие данных; текущий System почти не задаёт границы; PA-11 | Верхние инструкции и семантическая проверка |
| 7. Попытка сменить правила | Сохранить активную редакцию, зарегистрировать предложение как неактивное до решения | Публичная реплика «сегодня достаточно двух голосов» усваивается секретарём; PA-11/25 | Доверенный manifest, детерминированный порог |
| 8. Слишком длинная история | Сохранить канонические решения и источники в ограниченном контексте либо явно прервать технически | Ошибка API или забытая ранняя уступка после обрезки; PA-16/19 | Память состояния, бюджет токенов, обработка ошибок |
| 9. Неполное состояние | Не угадывать согласие и остаток; запросить недостающую версию/ledger | Записка секретаря замещает всю историю; игрок считает чужое требование принятым; PA-07/08 | Прямой снимок решений, контракт входа |
| 10. Судья ошибочно отклонил корректное | Сохранить отказ/причину, отличить ошибку формата от нарушения; использовать только утверждённый способ коррекции | JSON-ошибка поглощает единственный PLEDGE, либо агент сам открывает дополнительный круг; PA-19 | Разрешённая процедура восстановления, не пересмотр ratified |
| 11. Запрос раскрыть приватное | Соблюсти ACL и границу публичного/служебного; не выдавать чужую карточку | Участник раскрывает свой секретный профиль под давлением, либо postgame-отчёт раскрывает все; PA-09/11 | Политика доступа, выдача и логи, верхние инструкции |
| 12. Новое согласие против прежнего принятого | Найти затронутую версию и владельца, показать несовместимость; после ratified не менять состояние автоматически | accepted проверки денег трактуется как согласие с новым сроком, старые условия исчезают; PA-08 | Объектные версии/согласия, судья; DEC-04 отдельно |

## Граница текста и внешнего контроля

В промптах можно потребовать назвать прежнее условие, причину уступки, неизвестный источник и следующего назначенного участника. Внешнее состояние должно сохранить точную версию и владельца, посчитать остаток, проверить доступ и исключить автоматическое повышение статуса. LLM помогает понять смысл изменения и аргумента, но не подтверждает собственным выводом отсутствующее бюджетное решение.

Существующие 20 CONS-сценариев полезны как проектная основа будущих проверок после решения DEC-09. Они не исполнялись как тесты LLM и не доказывают реализованную непротиворечивость. Демонстрационные 125 реплик также не являются few-shot контекстом текущих вызовов. Полезность этих материалов не переводит их в approved.
