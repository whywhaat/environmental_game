# MVP переговоров
## Langflow
Запустите `docker compose -f langflow/docker-compose.yml up -d` и импортируйте
`langflow/Negotiation_MVP_5_players.json` через интерфейс Langflow на
`http://localhost:7860`. Граф содержит пять отдельных узлов моделей игроков,
модель конвертера, настройки проекта, оркестратор, отчёт и ChatOutput.
Узлы моделей по умолчанию обращаются к
`http://host.docker.internal:9090/v1`, модель `qwen3.8-9b-q4`; адрес и модель
можно изменить в каждом узле. Если API требует ключ, задайте `OPENAI_API_KEY`
в окружении контейнера; локальный API может работать без него.

Демонстрационный сценарий находится в `langflow/demo_config.json`: пять ролей,
смета 270 млн ₽ и 15 раундов. Параметры ролей редактируются в PlayerAgent;
каждый запуск сохраняет файлы в `games/<дата_и_время>/` на хосте, а Report
Controller показывает отчёт и пути к файлам. Для быстрой полной проверки с одним
раундом запустите `docker exec langflow python -u /app/negotiation_flow/smoke_run.py`.
Старые RAG и судья не участвуют в этом графе.

Самостоятельный Python 3.11+ движок переговоров; старый Langflow-код не требуется.

## Запуск

Задайте `OPENAI_BASE_URL` (адрес OpenAI-совместимого API с `/v1`), `PLAYER_MODEL` и `CONVERTER_MODEL`, а также `OPENAI_API_KEY`, если сервер требует ключ, затем запустите:

```powershell
python -m negotiation_mvp --config example_config.json --output result.json
```

Ответ локальной модели ожидается до 360 секунд; при таймауте тот же запрос выполняется ещё один раз. Лимит одного ожидания можно изменить через `OPENAI_TIMEOUT` (в секундах).

Каждый запуск создаёт отдельный каталог `games/<дата_и_время>/` с `result.json`, читаемым `result.md` и копией отчёта с точными сообщениями и ответами LLM `result_with_prompts.md`. Параметры `--output`, `--report` и `--prompt-report` задают имена файлов внутри каталога запуска, а `--games-dir` меняет расположение каталога `games`.
При техническом прерывании оба Markdown-файла сохраняют статус ошибки, а вариант с промптами также содержит уже состоявшиеся вызовы модели; JSON итогового результата в таком случае не создаётся.
Без `--output` полный JSON также печатается в стандартный вывод; состояние каждого раунда и таблица находятся в `rounds`, а итог — в `final_state`, `final_table`, `final_scores`, `votes` и `accepted`.

## Формат

Общая стоимость проекта вычисляется суммой `components[].cost` в рублях; `budget` и суммы `SET` тоже задаются в рублях, а `expected_own_share` — число от 0 до 1.
Каждый игрок задаёт желаемого ответственного за каждый платный компонент; все три назначения влияют на исходную сумму оценки на ±1, то есть на итоговый Score на ±10 баллов до ограничения шкалы.
Конвертер принимает строки вида `SET participants.industrial.contribution = 50000000`, `SET components.water_supply.responsible = "industrial"` или `NO_CHANGES`; на голосовании он извлекает из обычной реплики `SET participants.<id>.vote = true/false`, а при отсутствии однозначного решения возвращает `NO_CHANGES`.
Каждое поле `STATE` содержит список актуальных записей `value`, `player`, `seq`; разница значений означает конфликт, и такой список очищается перед следующим раундом.
Игроку передаются его `personal_context`, отдельные личные события `personal_history` и `motivation`, затем общая история `session`: в ней публикуются реплики и таблица после каждого раунда; чужие личные истории в общую сессию не попадают.
Его желаемая доля собственного взноса и ожидаемые ответственные за каждый компонент передаются отдельной личной записью, собранной из конфигурации; ожидания другого игрока не раскрываются.
В начале общей сессии объясняется формула оценки, а таблица показывает текущий `Score` от 0 до 100 и необходимый кредит для каждого участника. Общая часть за финансирование равна `(min(согласованные взносы, стоимость проекта) − стоимость проекта) / сумма бюджетов игроков`; если сумма бюджетов равна нулю, знаменатель заменяется стоимостью проекта. Score равен ограниченной диапазоном 0–100 величине `100 + 10 × (денежная часть + очки за ответственных + общая часть за финансирование) − штраф`; штраф равен 50 баллам до принятия договора и снимается после успешного голосования по полному договору. Взнос сверх бюджета допустим; кредит равен превышению взноса над бюджетом.
При отсутствии полного согласования игра идёт до `max_rounds`, после чего игроки всё равно голосуют; невыраженный голос считается воздержанием. Договор принимается только большинством при согласованном ответственном за каждый компонент, назначенных взносах всех игроков, покрытой стоимости проекта и отсутствии конфликтов.
В начале каждого раунда общая история сообщает его номер, лимит и число оставшихся раундов; в последних трёх раундах напоминает о близком голосовании, а в последнем прямо объявляет финальную возможность согласовать условия.
Суммы в речи игрока должны быть написаны цифрами, чтобы валидатор мог проверить числовую связь с командами конвертера.
Допустимые пути `SET` задаются конфигурацией. Если конвертер вывел неизвестный путь, ему даётся одна попытка исправления; после второй такой ошибки Python исключает все строки вне закрытого списка и проверяет остальные. Поэтому расчётный `participants.<id>.score` и несуществующий `components.<id>.contribution` не прерывают игру. Остальные строки проверяются по типам, значениям и числовым свидетельствам в реплике; если конвертер дважды добавил сумму без подтверждения, эта строка отбрасывается, а другие повторные ошибки прерывают запуск. Исходный ответ модели остаётся в отчёте с промптами, а обычный отчёт показывает применённые `SET`.
