# Переговорная игра «Экологическая ситуация в городе N»

Пять LLM-участников проводят общественные слушания: администрация, промышленный
холдинг, регион, жители и экологическая организация. Python проверяет действия,
ведёт финансовый план и условия протокола, затем организует голосование.
Дополнительный flow рассчитывает детерминированные последствия для города.

## Запуск в Langflow

Импортируйте один из файлов:

- `langflow/Negotiation_MVP_5_players.json` — переговоры и итоговый отчёт.
- `langflow/Negotiation_MVP_with_consequences.json` — переговоры, отчёт и модель последствий.

В PlayerAgent выберите модель через провайдер Langflow. Для существующего
локального Gpt2Giga используется OpenAI Compatible Base URL
`http://127.0.0.1:8090/v1`; ключ и модель настраиваются в провайдере и узлах игроков.
Прокси запускается из корня проекта:

```sh
./.venv/bin/gpt2giga --env-path ./gpt2giga.env
```

Эта команда предполагает уже установленный Gpt2Giga и заполненный локальный
файл настроек. Файл с ключами не хранится в Git. Для воспроизведения текущего
локального окружения используются установленные зависимости Langflow, LangChain,
langchain-openai, Pydantic и ChromaDB. Конфигурации Docker Compose в этой версии
репозитория нет.

## Формат и обработка ответов

Рабочая цепочка:

`PlayerAgent → LangChain structured output → нормализация → PlayerTurn → игровые правила → состояние`

LangChain вызывает одну функцию PlayerTurn через `with_structured_output`.
Для совместимости с Gpt2Giga модель получает простую транспортную схему без
объединений типов. Публичная речь находится в `speech`, действия — в отдельных полях:

- `own_contribution`: `action=unchanged/set`, `amount_millions` — взнос в миллионах рублей;
- `own_conditions`: собственные условия, их ID и значения;
- `pledge_demands` и `condition_demands`: денежные требования и требования условий к другим ролям;
- `responses`, `withdrawn_demands`, `addressed_to`, `vote`: ответы, отзывы, адресат и голос.

`everyone` означает обращение ко всем, `none` — отсутствие голоса вне голосования.
Строковые значения условий принимаются только из их допустимого списка.
Внутренний PlayerTurn проверяется Pydantic, затем правилами прав, бюджета и этапа.
Весь ход применяется атомарно. Нормализация не угадывает неизвестные ID, суммы или
смысл требований. Речь не используется для извлечения команд или обязательств.
Старый протокол текстовых команд и отдельная модель-конвертер удалены.

Одна попытка исправления получает исходные аргументы JSON и ошибки по полям.
После повторного нарушения контракта ход помечается `invalid_response`.
Сетевая ошибка после разрешённых повторов прерывает игру с частичным отчётом.

## Правила и сохранение

Игра проходит вступительные заявления, отдельные ходы торга, при дефиците —
Last Call, затем поимённое голосование. `max_rounds` настроек сценария определяет
лимит отдельных ходов торга, а не число полных кругов по пяти игрокам.
У каждого условия есть владелец; чужое условие можно потребовать, но менять
его может только соответствующая сторона.

По текущему коду протокол принимается большинством голосов даже при дефиците:
`budget_closed` и `deficit` сохраняются отдельно. Это поведение не изменялось
при очистке репозитория. Таблица отражает структурированные обязательства,
а не обещания, произнесённые только в речи.

Состояние, история, вызовы моделей, нормализация и ошибки сохраняются в
`games/<run_id>/result.json` и `result.md`. Корень задаётся `NEGOTIATION_GAMES_DIR`
или рабочим каталогом процесса Langflow. В Desktop это может быть
`~/.langflow/data/games/`. Статусы: `running`, `completed`, `failed`, `cancelled`.
ChatOutput получает итог после возврата результата оркестратора.

## Исходники и сборка

Основная игра: `negotiation_game/`. После изменения исходников:

```sh
python -m negotiation_game.build_component
```

Сборщик обновляет `dialog.py` и встроенный код в обоих JSON, сохраняя остальные
настройки и связи. Уже импортированный flow в Langflow обновляется отдельным
импортом. Генерируемые компоненты вручную не редактируются.

Модель последствий: `consequences_model/`; сборка —
`python -m consequences_model.build_component`. После её изменения flow
с последствиями обновляется через `consequences_model/build_flow.py`
в окружении с LFX. `langflow/build_demo_flow.py` — отдельный шаблонный генератор,
а не штатный способ обновления текущего графа; перед использованием нужно
сопоставить его набор узлов с текущим экспортом.

Прогноз по завершённому результату игры:

```sh
python -m consequences_model /path/to/result.json
```

Модель последствий рассчитывает исполнение обязательств, сроки ввода очистных,
состояние пяти подсистем, судьбы сторон и исход по фиксированным правилам.
LLM для расчёта не нужен; отдельный выход содержит промпт для литературного пересказа.

## Контекст агентов в Langflow

При подключённом и включённом RAG каждый агент получает полный набор общих
фактов корпуса (`area=shared`) и инструкций собственной роли (`area=role`,
с фильтром `audience`). Роль определяется по стабильному `id` игрока.
Этот обязательный блок передаётся на всех этапах: вступление, торг,
Last Call и голосование. Он читается из `corpus_b64`, не требует embedding API
и не обрезается по `top_k`. Отсутствующий или повреждённый обязательный
корпус прерывает запуск с понятной ошибкой.

Роль, стратегия, регламент поведения и контракт структурированного ответа
передаются системным сообщением. Контекст содержит текст фактов и ограничений
роли без технической обёртки, статусов проверки, примечаний каталога и указания
цитировать ID источников. Точные каталоговые заголовки и примечания из метаданных
не добавляются к тексту; содержательные ссылки внутри документов сохраняются.
ID использованных источников остаются во внутреннем `rag_retrievals`.
Публичная речь задаётся отдельно в `speech`; формат стенограммы не изменяется.

На вступлении и в торге семантический поиск добавляет до `top_k` справочных
фрагментов по текущей теме. Общие и ролевые материалы исключены из этой
выдачи, поскольку уже передаются полностью. На Last Call и голосовании
передаётся только обязательный блок. При сбое дополнительного поиска
обязательный контекст сохраняется.

Дополнительный поиск проверяет `index_policy`: явно разрешены записи с
`main_index`; отсутствие политики допускается только у существующих канонических
материалов (`shared`, `role`, `judge`, `methodology`). Отложенные политики
`reference_hold_not_main_index`, `analogy_reference_hold`, неизвестные значения
и внешние материалы без политики исключены. Ограничение применяется в Chroma,
при проверке результатов по локальному корпусу и в резервном Python-поиске.
Чужие роли не используются как запасной источник при пустой выдаче.

Метаданные Chroma содержат `search_enabled`; имя новой коллекции включает
`search_policy_v2`, поэтому прежняя коллекция не переиспользуется и не удаляется.
В текущем корпусе все 74 дополнительных внешних/правовых фрагмента отложены:
у игроков остаётся обязательный контекст, дополнительный поиск пропускается
без вызова embedding API (`skip_reason=no_allowed_sources`).

В `rag_retrievals` отдельно записываются `core_chunk_ids` (обязательный блок),
`chunk_ids` (дополнительная выдача), роль и `retrieval_status` (`ok`, `error`
или `skipped`). Это реализация RAG основной игры Langflow.


## Проверки

Из корня проекта, без вызовов GigaChat:

```sh
python -m unittest discover -s tests
```

В Python-окружении установленного Langflow:

```sh
python tests/verify_lf_player_turn.py
python tests/verify_lf_lifecycle.py
```

Первая проверка использует реальные LFX/ChatOpenAI и HTTP MockTransport;
вторая открывает временный локальный HTTP-сервер для проверки повторов,
таймаута и отмены. Они не расходуют квоту GigaChat и не доказывают качество
генерации реальной модели. Архитектурная проверка `test_no_legacy_pipeline.py`
проверяет отсутствие удалённых артефактов и старого протокола в runtime и JSON.

Исторические решения сохранены в `docs/adr/`; упоминания прежнего движка в них
не являются актуальными инструкциями запуска.
